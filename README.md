## **Smart Elevator Control System – ER Diagram**

## **Overview**

LiftGrid Systems develops intelligent elevator control platforms for large commercial infrastructures such as corporate towers, malls, airports, hospitals, and high-rise residential complexes. These environments operate multiple elevators simultaneously and require efficient management of ride requests, elevator allocation, maintenance activities, and performance monitoring.

This project presents the design of an Entity-Relationship (ER) diagram for a scalable, multi-building elevator management system. The database structure supports real-time operational tracking while preserving historical data for analytics and maintenance.

## **Objectives**

The primary objectives of this database design are:

* Manage multiple buildings connected to the platform.
* Maintain detailed information about floors within each building.
* Support multiple elevators operating inside each building.
* Track floor-level ride requests generated by users.
* Allocate requests to appropriate elevators.
* Record ride histories for analytical purposes.
* Monitor elevator status over time.
* Maintain comprehensive maintenance records without overwriting historical data.

## **Scope of the System**

The system is designed to answer operational and analytical questions such as:

* How many buildings are connected to the platform?
* How many elevators exist within each building?
* Which floors belong to a specific building?
* Which elevators serve particular floors?
* What requests were generated from which floors?
* Which elevator handled each request?
* Which requests are still pending?
* How many rides did an elevator complete during a specific period?
* Which elevator handled the highest number of requests?
* Can an elevator be temporarily disabled for maintenance?
* What is the maintenance history of each elevator?

## **Entities and Description**

### **Building**

Represents each infrastructure connected to the platform. A building can contain multiple floors, shafts, and elevators.

### **Floor**

Represents individual floors within a building. Each floor is uniquely identified within its building.

### **Shaft**

Represents the physical shaft in which an elevator operates. Each shaft is associated with one building and contains a single elevator.

### **Elevator**

Represents an elevator installed within a building. Elevators are associated with shafts and can serve multiple floors.

### **Elevator_Floor**

A junction entity that models the many-to-many relationship between elevators and floors, allowing multiple elevators to serve the same floor and vice versa.

### **Floor_Request**

Captures ride requests generated by users, including the source floor, destination floor, direction, time of request, and current status.

### **Ride**

Represents the allocation of a floor request to a specific elevator. Each request results in a single ride assignment.

### **Ride_Log**

Maintains historical information about completed rides, including pickup and drop-off floors, ride duration, and other analytical metrics.

### **Elevator_Status_Log**

Tracks changes in elevator status over time, such as **IDLE**, **MOVING**, **MAINTENANCE**, or **OUT_OF_SERVICE**, ensuring that operational history is preserved.

### **Maintenance_Record**

Stores detailed maintenance information for each elevator, including scheduled and completed dates, type of maintenance, technician details, and status.

## **Relationships**

* A **Building** contains many **Floors**.
* A **Building** contains many **Shafts**.
* A **Building** contains many **Elevators**.
* Each **Shaft** contains exactly one **Elevator**.
* **Elevators** and **Floors** share a many-to-many relationship through **Elevator_Floor**.
* A **Floor_Request** originates from one floor and targets another.
* Each **Floor_Request** is assigned to one **Elevator** through a **Ride**.
* An **Elevator** can complete many **Rides**.
* An **Elevator** can have multiple **Status Logs** over time.
* An **Elevator** can have multiple **Maintenance Records**.

## **Design Considerations**

### **Separation of Static and Dynamic Data**

Configuration entities such as **Building**, **Floor**, and **Elevator** are separated from dynamic operational data like **Floor_Request**, **Ride**, and **Ride_Log**.

### **Historical Data Preservation**

Status and maintenance information are stored in dedicated tables to ensure that historical records are never overwritten.

### **Scalability**

The schema supports expansion to multiple buildings and can efficiently handle a high volume of ride requests and operational data.

### **Flexibility**

The many-to-many relationship between elevators and floors allows the system to adapt to different architectural layouts and zoning requirements.

### **Data Integrity**

Primary and foreign key constraints enforce referential integrity and maintain consistency across the database.

## **Conclusion**

This ER diagram provides a robust and scalable foundation for managing intelligent elevator operations across multiple buildings. The design supports real-time monitoring, efficient ride allocation, and long-term analytical insights, making it well suited for large-scale infrastructure environments.
